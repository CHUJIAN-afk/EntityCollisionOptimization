# 技术细节：ecopt 做了什么，与 Lithium / 加速碰撞怎么配合

> 实测数据全部来自实机测试（猪为正常 AI 与重力，仅关闭挤压伤害；掉落物为静止不动的 4000 个物品实体），
> 表中数值为测试用例的耗时，越小越好。

## 1. 定位：碰撞链路上的四层

一次实体碰撞在服务端要经过四段彼此独立的工作，不同模组各占其中一两段：

| 层 | 工作内容 | 参与者 |
| --- | --- | --- |
| ① 实体查询层 | 从实体段存储里找出"可能与本次碰撞有关"的实体 | ecopt、Lithium |
| ② 移动/方块碰撞层 | 沿三轴做方块碰撞扫描、决定位移被挡多少 | Lithium |
| ③ 方块状态读取层 | 扫描过程中反复读同一个方块位置的状态与形状 | ecopt、Lithium |
| ④ 实体间挤压/推挤计算层 | 密集实体互相推挤的成对计算 | **加速碰撞** |

* **ecopt 主要在 ① 与 ③**：段级增量表 + 方法级接管实体查询，区块级方块状态缓存；
* **Lithium 横跨 ①②③**；
* **加速碰撞（accelerated recoiling）在 ④**：用 C++ 与 GPU 承担实体间挤压（成对推挤）的密集计算，
  目标是显著降低实体密集区域的碰撞开销。它不负责"找出要参与计算的实体"，
  因此 ① 的效率直接决定它能不能吃满 —— 这正是实测中它与 ecopt/Lithium 强互补的原因。

## 2. 与 Lithium 的逐层对比

| 维度 | Lithium | ecopt |
| --- | --- | --- |
| 实体碰撞查询 | 类分组增量表（`ClassGroupFilterableList`）+ 把实体查询推迟到方块扫描之后 | 段级增量表（可碰撞 / 可推挤两类），`getEntityCollisions` 方法级整体接管 |
| 推挤查询 | 每段掩码表 + 引用掩码列表，过滤门槛随段内实体数自适应 | 段级增量表；同点被 Lithium 占用时自动让位 |
| 方块碰撞扫描 | 覆写 `collideBoundingBox`：推迟实体查询、支持方块短路、单轴薄盒、区块感知扫描器、形状偏移缓存 | 不改扫描器 |
| `noCollision` | 覆写 `Level.noCollision`（方块 → 硬实体惰性列表 → 世界边界） | 三重循环扫方块 + 空气/空形状早退 + 整方块 AABB 早退 + 命中即返回 |
| 方块状态读取 | 方块追踪 + 实验性 block caching（默认关闭） | 区块级缓存，同 tick + 段版本号双重校验，覆盖所有区块级读取 |
| 实体段遍历 | 不改 `EntitySection.getEntities` | 直接遍历内部 ArrayList、覆盖式查询跳过、段内 2³ 子格索引 |
| 支撑方块 | 短路逻辑在 `collideBoundingBox` 内 | `Entity.collide` 入口的竖直下落捷径（先探中心列） |
| 兼容方式 | 原生 `@Redirect` / `@Overwrite` | MixinExtras `@WrapMethod` / `@WrapOperation`，同点 `require/expect = 0` 让位 |

**重叠与分工（两者同时安装时）**

* 推挤：Lithium 的注入占点，我们的自动让位 → 只跑一条，不重复计算；
* 实体碰撞查询：我们方法级接管，Lithium 在该方法内部的注入不再执行 → 只跑一条；
* `noCollision`：Lithium 覆写 `Level.noCollision` 优先，我们的接口包装不参与；
* 独有部分各自生效：我们的段级增量表、方块缓存、子格索引；Lithium 的方块追踪、延迟实体查询、方块扫描器。

## 3. 实测：4000 只猪 3×3 挤压（移动实体 + 推挤）

| 配置 | 耗时 | 相对原版 |
| --- | --- | --- |
| 原版 | 1132 ms | 1.00× |
| 锂 | 725 ms | 1.56× |
| **ecopt** | **650 ms** | **1.74×** |
| 加速碰撞 | 419 ms | 2.70× |
| 锂 + ecopt | 637 ms | 1.78× |
| 加速碰撞 + 锂 | 70 ms | 16.2× |
| 加速碰撞 + ecopt | 72 ms | 15.7× |
| **加速碰撞 + 锂 + ecopt** | **54 ms** | **21.0×** |

读法：

1. 单独安装时 **ecopt 比 Lithium 快约 10%**（650 / 725），两者解决的是同一层问题；
2. 两者同时安装 637 ms，比 Lithium 快 12%、比 ecopt 快 2% —— 重叠部分只跑一条，属于互补而非叠加；
3. 加速碰撞把 ④ 的成对推挤计算搬到 C++/GPU 后，**瓶颈立刻转移到 ① 的实体收集**：
   单独用它只有 419 ms（2.70×），配上 Lithium 是 70 ms、配上 ecopt 是 72 ms（16× 级别）；
4. 在"加速碰撞 + Lithium"之上再加 ecopt 仍有 **70 → 54 ms（−23%）**，
   说明我们的实体收集比 Lithium 更轻（段级增量表 + 方法级接管），是三者齐全时的主要增益来源。

## 4. 实测：4000 个静止掉落物（实体查询的极端场景）

| 配置 | 耗时 |
| --- | --- |
| 原版 | 378 ms |
| 锂 | 7 ms |
| **ecopt** | **7 ms** |
| 加速碰撞 | 197 ms |
| 加速碰撞 + 锂 | 8 ms |
| 加速碰撞 + ecopt | 9 ms |
| 锂 + ecopt | **5 ms** |
| 加速碰撞 + 锂 + ecopt | 7 ms |

读法：

1. 静止堆积是"实体查询层"的极端场景：**ecopt 与 Lithium 打平（各 7 ms，约 54×）**；
2. 加速碰撞只有 197 ms（1.9×）：掉落物不做互相推挤，**④ 层没有计算可以卸载到 GPU**，
   它的收益自然只体现在有挤压行为的场景（下节的猪）；这不是它的短板，而是适用面问题；
3. 加上 Lithium 或 ecopt 后是 8 / 9 ms —— ① 层被优化后，静止堆积场景逼近极限；
4. 锂 + ecopt 的 5 ms 是全场最优，说明两者的增量表在候选集合上有互补
   （我们按类过滤，Lithium 按段掩码）。

## 5. 结论

* **只装一个时**：移动实体（猪）场景 ecopt 略优于 Lithium（650 vs 725）；静止堆积场景两者持平（7 vs 7）。
* **一起用时**：不重复计算，猪 725 → 637（−12%）、掉落物 7 → 5（−29%）。
* **与加速碰撞搭配**：它的 C++/GPU 挤压计算层（④）是密集挤压场景的最大增量（419 ms），
  但一旦 ④ 不再是瓶颈，**① 实体收集就成了新的瓶颈** —— 这正是它必须搭配 ecopt 或 Lithium 的原因
  （419 → 70 / 72 ms，三者齐全 54 ms）。
  静止堆积场景没有挤压计算可卸载（197 ms，1.9×），优化 ① 才是正解（7 ms，54×）。
* **推荐**：以加速碰撞 + Lithium 为基础时，**ecopt 仍值得再加**（猪场景再降 23%，掉落物场景持平最优）。
